# PoC 実測結果と、そこから確定した設計判断

計測日: 2026-09-13
計測機: Windows 11 / 論理16コア / RAM 68.3GB / ffmpeg 9.0 / OpenCV 5.0.0 / Python 3.13
供試カメラ: ELECOM 2MP Webcam（現時点で接続されている唯一の物理USBカメラ）

> **注意: これは 1 台での計測です。** 最優先リスクである「4台同時取得の成立性」は
> カメラが揃っていないため**未検証**。以下は 1 台で分かった事実に限る。

---

## F-1. 露出のオート制御が fps を 1/3 に落とす（最重要）

FHD MJPEG での実効フレームレート:

| 露出設定 | 実効 fps |
|---|---|
| オート露出（既定） | **10.0** |
| 手動 2^-5 秒 (31.2ms) | 23.3 |
| 手動 2^-6 秒 (15.6ms) | 28.8 |
| 手動 2^-7 秒 (7.8ms) | **29.2** |

暗所でオート露出が露光時間を延ばし、その結果フレーム間隔が伸びる。
解像度を 1920x1080 → 1280x720 → 640x480 と下げても 10fps のまま変わらなかったため、
**これは帯域の問題ではなく露出の問題**と切り分けられる。

**設計判断:** 露出の手動固定は任意設定ではなく **MUST**。
加えて短い露光はモーションブラーを抑えるため、接触判定の精度にも直結する。
その代償として映像が暗くなるので、**会場照度が要件**になる（要確認事項）。

## F-2. FHD30 は MJPEG でしか出せない

供試カメラの対応モード（全12モード）:

- MJPEG: 1920x1080 / 1280x720 / 640x480 / 640x360 / 352x288 / 320x240 / 176x144（すべて30fps）
- YUY2 (非圧縮): **640x480 以下のみ**

**設計判断:** カメラ要件は「MJPEG で 1920x1080@30 出力可能」。
非圧縮での FHD は選択肢として存在しない。当初の帯域計算（YUY2 の FHD は
約124MB/s で USB2 に1台も乗らない）は、そもそもカメラ側が提供していない。

## F-3. OpenCV では無変換録画（remux）ができない

- `cv2.VideoWriter` に MJPG を指定しても、実際には **デコード→再エンコード** される。
  実測: 1フレーム約12.6KB（ffmpeg の `-c:v copy` では約145KB）＝ 画質が落ちている。
- `CAP_PROP_CONVERT_RGB=0` で生JPEGを取り出す試みは、設定自体は成功を返すが
  読み出すと**デコード済みBGR**が返る（先頭バイトが `ffd8` にならない）。
  DirectShow バックエンドがこのプロパティを尊重しない。

**設計判断: 録画経路から OpenCV を外す。**
録画は **ffmpeg サブプロセス（カメラごとに1つ）が `-c:v copy` で直接担当**し、
OpenCV はプレビュー/解析専用にする。

## F-4. ffmpeg 1プロセスで「無劣化録画」と「プレビュー供給」を同時に出せる

検証済みの構成（1プロセス・2出力）:

```
ffmpeg -f dshow -vcodec mjpeg -video_size 1920x1080 -framerate 30 -i "video=<name>"
  -map 0:v -c:v copy -f segment -segment_time 5 -reset_timestamps 1 \
      -strftime 1 recordings/cam0_%Y%m%d-%H%M%S.mkv     # 無劣化・常時録画
  -map 0:v -vf scale=480:-2 -pix_fmt bgr24 -f rawvideo - # プレビュー用（stdout）
```

結果: セグメントファイルが連続生成され、同時に Python 側が縮小フレームを
継続受信できた。

**設計判断:** これを本システムの取得層とする。利点は、
- 録画パスにデコードコストが一切かからない（落としてはいけない経路が最も軽い）
- セグメント分割により、プロセスが落ちても既に閉じたセグメントは壊れない
- 「試合開始10秒前」はセグメント境界とタイムスタンプから後で切り出せる
- プレビューは縮小済みで届くので UI 側の負荷が小さい

## F-5. USB コントローラが単一

`Intel(R) USB 3.1 eXtensible Host Controller - 1.10` の配下にカメラが接続されている。
このマシンで見えたUSBコントローラは実質1系統であり、**4台を別バスに分散できない可能性が高い**。
4台同時取得の帯域検証（B-2）で最も効いてくる点なので、実機4台での再計測が必須。

## F-6. 計測環境がバックグラウンドアプリで汚染されている

1台取得中のシステム全体CPUが平均93%・最大100%に達したが、
**本システムのプロセスCPUは平均7.7%**にすぎなかった。内訳:

| プロセス | CPU(16コア正規化) |
|---|---|
| wintracker | 11.7% |
| svchost | 10.5% + 6.8% |
| code (VS Code) | 8.0% + 6.6% |
| discord | 6.8% |
| spotify | 5.9% |
| com.docker.backend | 3.6% |

このCPU枯渇が取得を阻害し、手動露出でも 29.2fps → 24.6fps（ドロップ14%）に低下した。

**設計判断:** 「大会運用時はバックグラウンドアプリを停止する」ことを**運用要件**とする。
また、**B-2 の本計測はクリーンな状態で実施しないと意味がない。**

## F-7. RTMP 取得（追加要件）

映像入力を RTMP でも受けられるようにする要件が追加された。
送出元は**別PCに既に立っている RTMP サーバー**であり、こちらは
**購読するクライアント**として繋ぐ。受信サーバーを自前で立てる必要はなく、
MediaMTX や nginx-rtmp の追加導入も不要（ffmpeg の rtmp プロトコルで足りる）。

### 低遅延設定の効果（1280x720@30 を 26 秒送出して実測）

| 入力オプション | 初フレームまで | 定常fps | 受信率 |
|---|---|---|---|
| `-analyzeduration 1M -probesize 1M` | 2.98s | 30.0 | 94% |
| `-analyzeduration 0 -probesize 32k` | **1.69s** | 30.0 | **98%** |

**定常状態はどちらも 30.0fps で安定しており、遅延は蓄積しない。**
後者を既定に採用した（`FfmpegSource.from_rtmp(low_latency=True)`）。
解像度を確定できないストリームに当たった場合の逃げ道として
`low_latency=False` を残してある。

### 録画は無劣化コピーのまま通る

RTMP は H.264 で届くため `-c:v copy` でそのまま保存できる。
検証で生成されたセグメントは `h264 1280x720` を保持しており、再エンコードなし。

**ストレージ面では MJPEG より大幅に有利。** USB+MJPEG の約58GB/時に対し、
H.264 なら同条件で1桁小さい。F-4 の構成（1プロセスで録画＋プレビュー同時出力）は
入力を差し替えるだけでそのまま成立する。

### 4系統同時受信を UI まで通して確認

4本の RTMP を同時購読し、4分割表示・タグ打ち・録画まで通ることを確認した。
このときの4系統間の受信時刻ずれは **15.1 ms**。
ただしこれはローカルループバック（同一PC内）での値であり、
**実ネットワーク経由・実機エンコーダでは大幅に悪化する**ので、本番構成での再測が必要。

### 注意点

1. **起動直後の受信時刻は撮影間隔を表さない。**
   溜めたぶんを速く吐くため、一瞬 47fps 相当の burst が出る。
   定常状態に入れば 30fps に落ち着く。
2. **`drop_rate` 指標は RTMP では当てにならない。**
   受信間隔から欠落を推定する方式のため、上記 burst やネットワークジッタを
   ドロップとして数えてしまう（UI 上で 8〜30% と表示された）。
   RTMP のフレーム欠落は別の方法（ストリームのPTS連続性）で見る必要がある。**未対応。**
3. **RTMP はカメラ間同期の精度で USB に劣る。**
   送出端末ごとに独自のエンコーダ・バッファ・クロックを持つため。
   接触判定で複数カメラを突き合わせる用途では、この誤差が効いてくる。
4. **切断からの自動復帰は実装済み**（`FfmpegSource._maybe_restart`）。
   検証でも送出終了時に再接続動作が走ることを確認した。
