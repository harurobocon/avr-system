## 1. このプロジェクトは何か

ロボコン向けの VAR（Video Assistant Referee）システム。目的は2つ。

1. 試合のハイライトシーンを配信映像に乗せる
2. 審判が試合中〜直後に映像で判定を確認できるようにする

元の要求ドラフトは `docs/requirements-draft.md`（旧 README.md の内容をそのまま保存）。
**正式な要件定義書はまだ書いていない。** これが残タスクのひとつ。

## 2. 確定している前提（ユーザー回答による）

| 項目 | 決定 |
|---|---|
| 技術スタック | Python + ffmpeg / OpenCV、UI は PySide6 |
| **映像入力** | **RTMP を主とする。別PCに既設の RTMP サーバーから購読する** |
| USBカメラ | 併用可能だが主役ではない |
| 試合タイマー連携 | [RoLIMOA](https://github.com/kishimotonico/RoLIMOA)（WebSocket で Redux action を同期）。**未実装** |
| UI構成 | 1台1画面でオペレータ1名が兼用 |
| 同期精度 | 現実的に達成できる最高精度（受信時刻によるソフト同期） |
| 録画方式 | 常時録画 + 後から試合区間を切り出し |
| 進め方 | 時間制約があるため、UI設計と技術実証を**並行**で進める |

## 3. 設計判断と、その根拠（機種に依存しない結論）

詳細な実測値は `poc/results/FINDINGS.md` を参照。

| # | 判断 | 理由 |
|---|---|---|
| F-1 | **カメラの露出は手動固定が必須** | オート露出は暗所で露光を延ばし、FHD30 が **10fps** まで落ちた（手動 1/128秒なら 29.2fps）。解像度を落としても改善せず、帯域ではなく露出の問題と切り分け済み。短い露光はモーションブラーも抑え接触判定に有利だが、**会場照度が前提条件**になる |
| F-2 | **USBカメラ要件は「MJPEG で FHD30」** | 供試カメラは非圧縮(YUY2)だと 640x480 が上限。FHD は MJPEG でしか出ない |
| F-3 | **録画経路から OpenCV を外す** | `cv2.VideoWriter` は MJPG 指定でも再エンコードしていた（1フレーム12.6KB vs ffmpeg copy の145KB）。`CAP_PROP_CONVERT_RGB=0` による生JPEG取得も DirectShow が無視する |
| F-4 | **ffmpeg 1プロセスで録画とプレビューを同時に出す** | `-c:v copy` のセグメント録画と、縮小 rawvideo の stdout 出力を1プロセスで両立できることを実証。録画パスにデコードコストがかからない |
| F-5 | USBコントローラが単一だと4台分散できない | 開発機では1系統しか無かった。**本番PCで要確認** |
| F-6 | **大会時はバックグラウンドアプリを止める**（運用要件） | 開発機ではVS Code/Discord/Spotify/Docker がCPUを食い、本システム自体は7.7%しか使っていないのに取得が阻害された |
| F-7 | **RTMP は購読するだけでよい。受信サーバーの自前構築は不要** | ffmpeg の rtmp プロトコルで足りる。MediaMTX / nginx-rtmp は不要。H.264 で届くので `-c:v copy` でそのまま保存でき、ストレージは MJPEG より1桁小さい |

### RTMP の低遅延設定（採用済み）

| 設定 | 初フレーム | 定常fps | 受信率 |
|---|---|---|---|
| `-analyzeduration 1M -probesize 1M` | 2.98s | 30.0 | 94% |
| **`-analyzeduration 0 -probesize 32k`（採用）** | **1.69s** | 30.0 | **98%** |

定常状態では遅延が蓄積しないことを確認済み。

## 4. コード構成

```
core/
  frame_source.py    … 全入力の共通インターフェース（FrameSource / Frame / Capabilities / SourceStats）
                        UI はこれにしか依存しない。入力方式を差し替えても UI は無変更
  ffmpeg_source.py   … ★本命の取得層。RTMP / RTSP / USB(dshow) を同じ扱いにする
                        1プロセスで「無劣化セグメント録画」＋「縮小プレビュー」を同時に出す
                        切断時の自動再接続つき。probe_stream() で疎通確認もできる
  uvc_source.py      … OpenCV 直叩きの USB カメラ取得（露出固定を内蔵）。プレビュー/計測用
  synthetic_source.py… カメラ不要の合成映像。フレーム番号を焼き込み、
                        切断/フリーズ/ドロップを注入できる。UI 開発と異常系検証用
  timeline.py        … リングバッファと再生ヘッド。取得スレッドと再生を完全分離する要
                        4分割の同期（最近傍フレーム）、コマ送り、ライブタギングもここ
ui/
  main_window.py     … オペレータ画面。--source でソースを切り替える
  viewer.py          … 映像表示（ズーム/パン、状態バッジ）
poc/
  enumerate_cameras.py … 接続カメラの能力と USB トポロジを列挙
  capture_bench.py     … 同時取得の帯域/CPU/ドロップ/カメラ間ずれを実測
  results/FINDINGS.md  … ★実測結果と設計判断の記録。まずこれを読む
docs/
  HANDOVER.md          … 本書
  requirements-draft.md… 元の要求ドラフト（旧 README.md）
  ui/shortcuts.md      … 操作モデルとキーボードショートカット定義
  ui/mock*.png         … UI のスクリーンショット
```

### 実装済みの UI 機能

4分割 ⇔ 単一全画面、タイムスライダー、時刻直接入力、コマ送り、
任意倍速（プリセット6段 + 0.05〜4.00x 連続）、ホイールズーム/ドラッグパン、
ライブタギングとタグ一覧からのジャンプ、カメラ状態表示（LIVE/FREEZE/切断）。

検証済み: 4台同期ずれ 0.20ms（合成）、コマ送り ±1 の seq 連番・往復一致、
倍速の進行量が rate に比例、録画継続中の過去区間再生、異常系の状態遷移。

**コマ送りは「時刻 + 1/fps」ではなく実フレームを辿る実装**にしてある
（`FrameBuffer.step()`）。フレーム落ちがあっても必ず隣の実フレームに移動でき、
「送ったのに絵が変わらない」が起きない。

## 5. 本番PCでの環境構築

前提: **ffmpeg と ffprobe に PATH が通っていること**（本システムの中核）。

```bash
# Python は 3.12 以降のネイティブ Windows 版を使う。
# ※ MSYS2/mingw の python では PyPI の Windows wheel が入らないので注意
#   （開発機では PATH 先頭が mingw python で一度ハマった）
python -m venv .venv
./.venv/Scripts/python.exe -m pip install -r requirements.txt

# 動作確認（カメラ不要・合成映像）
./.venv/Scripts/python.exe -m ui.main_window --source synthetic:4 --fault
```

`--fault` を付けると 10秒後に cam1 がフリーズ、15秒後に cam2 が切断、25秒後に復帰する。
異常系の見え方を確認できる。

## 6. 本番PCで最初にやること

### 6-1. 環境の再計測（F-5 / F-6 の確認）

```bash
# 接続カメラと USB コントローラ構成を確認
./.venv/Scripts/python.exe poc/enumerate_cameras.py --probe
```

USBカメラを使うなら、**バックグラウンドアプリを止めてから**：

```bash
./.venv/Scripts/python.exe poc/capture_bench.py --cameras 0,1,2,3 --ramp --duration 120
```

### 6-2. RTMP の実ネットワーク計測（最優先・未検証の最大の穴）

本番の RTMP サーバーの URL が分かり次第：

```python
from core.ffmpeg_source import probe_stream
print(probe_stream("rtmp://<host>/<app>/<key>"))   # 疎通・解像度・fps・コーデック
```

```bash
./.venv/Scripts/python.exe -m ui.main_window \
  --source "rtmp://host/live/cam0,rtmp://host/live/cam1,rtmp://host/live/cam2,rtmp://host/live/cam3"
```

**確認すべきは「実ネットワーク経由でのカメラ間同期ずれ」。**
開発機で得た 15.1ms は同一PC内ループバックの値で、実運用では大幅に悪化する。
ここが VAR の判定精度を決めるので、RTMP 主体構成の可否はこの数値次第。

## 7. 未解決の問題・既知の制約

| 重要度 | 内容 |
|---|---|
| 高 | **実ネットワークでの RTMP 同期ずれが未測定。** RTMP は送出端末ごとに独自のエンコーダ・バッファ・クロックを持つため、USB より原理的に精度が落ちる。接触判定で複数カメラを突き合わせる用途に耐えるかは未知 |
| 高 | **要件定義書が未作成。** 章立ての方針は `docs/requirements-draft.md` と本書に材料が揃っている |
| 高 | **RoLIMOA 連携が未実装。** 受信する action から試合開始/終了をどう判定するかも未調査。連携断時に手動トリガで代替できることを MUST にする方針 |
| 中 | **`drop_rate` 指標が RTMP では当てにならない。** 受信間隔から欠落を推定する方式のため、起動時バーストやネットワークジッタを誤検出する（UI 上で 8〜30% と表示された）。本来はストリームの PTS 連続性で見るべき |
| 中 | **「試合開始10秒前〜終了10秒後」の切り出しが未実装。** 常時セグメント録画までは動く。セグメント境界とタイムスタンプから切り出す設計 |
| 中 | **配信出力（NDI / 仮想カメラ）が未実装。** UI にセレクタは置いてあるが中身は無い |
| 低 | RTMP 切断からの自動復帰は実装済みだが、実ネットワークでの挙動は未検証 |
| 低 | 会場照度の要件値が未確定（F-1 の帰結） |

## 9. 会話の中で決まった重要な経緯

- 当初は「要件定義 → 実装」の直列進行を計画したが、時間制約により
  **UI設計と技術実証の並行**に切り替えた。並行を可能にするために
  `FrameSource` 抽象を最初に作り、UI は合成映像で先行開発した
- 当初は OpenCV で取得・録画する想定だったが、**実測により ffmpeg サブプロセス方式へ変更**（F-3/F-4）
- 当初は USB カメラ4台構成の想定だったが、**RTMP 主体に変更**。
  別PCに RTMP サーバーが既設のため、こちらは購読側に徹する
- 開発機には物理USBカメラが1台（ELECOM 2MP Webcam）しか繋がっておらず、
  4台同時取得の成立性検証はできていない
